# ドライブトラベルプランナー（MVP）

要件定義書の29章「Claudeへの実装方針」に沿って段階的に実装しています。
モバイル・PCの両方での利用を想定し、単一のNext.jsアプリ（レスポンシブWeb）として構築しています。

**移動手段は自動車のみに対応しています。** 公共交通機関(TRANSIT)は、Google Directions/Routes APIが
日本国内では経路を返さないケースがあるため(Google公式フォーラムでも報告されている既知の制限)、
現時点ではサポートしていません。

## 実装済み

- **Web版（Vercel）とAndroid/iOSアプリ（Capacitor）を同一コードベースで提供**（詳細は下記「モバイルアプリ(Capacitor)構成」参照）
- 旅行の作成・一覧、データの永続化（Postgres）（4章）
- **旅行一覧からの削除**（登録済みの行きたい場所・生成済みプランも合わせて削除）
- **旅行の日程（開始日・終了日）を後から変更可能**（同じ日付が残っていれば、日ごとの活動時間・出発地/到着地の設定を引き継ぐ。生成済みのプランは日付・日数に依存するためリセットされる）
- 場所の検索・重複登録防止・一覧表示（5章）
- Google Placesからの詳細情報の都度取得（住所・Google Mapsリンク）（6章・7章）
- **旅行日程の実日付に対応した営業時間表示**（全曜日ではなく、実際にその旅行で訪れる日付分だけを計算して表示）
- **祝日の注意書き**（旅行期間中に日本の祝日が含まれる場合、営業時間が通常と異なる可能性がある旨を警告表示）
- **旅程設定**：**日ごと**の出発地・到着地（到着地を変更すると翌日の出発地に自動的に引き継がれる）、活動ペース（ゆっくり/せかせか）、経路の希望（速さ優先/安さ優先=有料道路回避）、日ごとの活動時間（8〜10章）
- **旅程プランの自動生成**（11〜17章）：Google Routes APIで実測の移動時間を取得し、営業時間・活動時間内に収まるよう機械的に巡回順を決定
  - AIは使用せず、決定的なアルゴリズムのみで実装（「締切（閉店時刻）が近い場所を優先する」という要件書12章の考え方をそのままロジック化）
  - リアルタイム交通状況は考慮しない設定（`TRAFFIC_UNAWARE`）。未来の旅程計画のため、統計的な標準所要時間を使用
  - 訪問できない場所がある場合は理由付きで警告表示（17章）
- **各訪問地周辺の駐車場候補を検索**（月極駐車場は名称から除外、名所からの距離順）。訪問地の横にある「周辺駐車場」ボタンで一覧を開き、選ぶとその駐車場までの運転時間・そこから名所までの徒歩時間（往復）を旅程に反映し、以降の時刻を自動でずらす（日程・訪問順序は変更しない）
- **有料道路の通行料金（ETC・現金）を表示**：速さ優先の場合、実際に使う区間の通行料金をETC・現金の両方で取得して表示（安さ優先=有料道路回避の場合は取得しない）
- **プランをGoogleマップで開くリンク**（出発地→各訪問地→到着地の経路を日ごとに表示。Place IDを使って正確な地点にリンクするため、道路上の最寄り点にズレる問題を回避）
- **KMLファイルのダウンロード**：Googleマイマップにインポートすることで、生成したプランをGoogleアカウント上に地図として保存できる
- **旅程のエクスポート**：Word（.docx）、Excel（.xlsx）、印刷/PDF保存（ブラウザの印刷機能を使用）、カレンダー（.ics、Googleカレンダー等にインポート可）、テキスト（.txt）から選んでダウンロード可能
- **有料道路の通行料金（ETC・現金）を表示**。片方のみデータが取得できない場合は「不明」と表示し、0円と誤表示しない
- APIキーをサーバー側（API Routes）に隠す構成（22章）

### ルート生成アルゴリズムについて

`lib/planner.ts` に実装しています。各日について、現在時刻・現在地から「営業時間内かつ活動時間内に訪問できる場所」を洗い出し、その中から**閉店時刻が最も早い場所を優先**して組み込んでいく貪欲法です。移動時間はGoogle Routes APIの実測値（リアルタイム交通は考慮しない標準所要時間）に、活動ペースに応じたバッファ（駐車等の余裕・移動時間の割り増し）を加えて計算しています。「安さ優先」を選ぶと、有料道路を回避した経路で計算します。

滞在時間が未設定の場所は、Google Places APIの施設種別（`primaryType`。例: 美術館・遊園地・寺社・ショッピングモール等）から、施設の性質に応じた目安滞在時間を算出します（`lib/stay-duration.ts`）。さらに活動ペースに応じて倍率をかけます（ゆっくり=1.3倍、せかせか=0.7倍）。施設種別が取得できない場合は汎用デフォルト（標準60分基準）にフォールバックします。

### 通行料金について

通行料金の計算リクエストは、通常の移動時間リクエストより課金レートが高く設定されています（Google公式ドキュメントに明記）。そのため、探索中の候補全てではなく、**実際に採用が確定した区間だけ**通行料金を取得するようにしています。「安さ優先」（有料道路回避）の場合は取得自体を行いません。

### Googleへの保存について

「保存」は、GoogleがサードパーティアプリからGoogleマップの個人アカウントへ直接書き込めるAPIを公開していないため、完全自動化はできません。代わりに、生成したプランをKML形式でダウンロードし、[Googleマイマップ](https://mymaps.google.com/)にインポートする形で、Googleアカウント上に地図として保存できるようにしています。

## セットアップ

```bash
npm install
cp .env.local.example .env.local
# .env.local に Google Cloud の APIキーを設定
npm run dev
```

http://localhost:3000 で確認できます。

### 必要なGoogle Cloud設定

1. Google Cloud Consoleで以下の2つのAPIを有効化する
   - **Places API (New)**（旧版の「Places API」とは別物なので注意。駐車場検索(Nearby Search)にも使用）
   - **Routes API**（移動時間の取得に使用）
2. APIキーを発行し、`.env.local` の `GOOGLE_MAPS_API_KEY` に設定
3. APIキーの「APIの制限」に、上記2つのAPIを両方チェックする
4. 本番運用時は、キーにAPIリファラ制限・IPアドレス制限などのアプリケーション制限を必ず設定する（要件書22章）
5. 課金（Billing）が有効なプロジェクトであることを確認する（両APIとも無料枠はあるが課金有効化は必須）

### 祝日データについて

`lib/holidays.ts` で、キー不要の無料API（holidays-jp）から日本の祝日一覧を取得しています。追加設定は不要です。取得に失敗しても旅行プランナー自体は問題なく動作します（祝日警告が表示されないだけです）。

## データの保存について

旅行・登録場所・旅程設定・生成済みプランは、**Postgres（Vercel Postgres / Neon等）** に保存されます（`lib/db.ts`）。

以前はローカルファイル（`data/db.json`）への書き込みで代用していましたが、Vercelのサーバーレス関数は実行環境のファイルシステムが読み取り専用のため、本番デプロイ後に保存が全て失敗する不具合がありました。マネージドPostgresへの永続化に置き換えることで解消しています。

### セットアップ

1. VercelプロジェクトのStorageタブから「Postgres」（Neon経由）を追加する、またはNeon等で自前にデータベースを作成する
2. Vercelに接続していれば `POSTGRES_URL` 等の環境変数は自動的に設定される
3. ローカル開発では `vercel env pull .env.local` を実行するか、`.env.local` に `POSTGRES_URL` を手動で設定する（`.env.local.example` 参照）
4. テーブル（`trips` / `trip_places`）は初回アクセス時に自動作成されるため、手動でのマイグレーションは不要

### スキーマ設計について

既存の型定義（`Trip`・`TripPlace`）が持つネストした構造（`day_configs`・`plan`等）をそのまま活かせるよう、テーブルを細かく正規化せず「1行＝1トリップ分のJSONB」として保存しています。将来的にユーザーごとのデータ分離（認証）が必要になった場合は、`trips`テーブルに`user_id`列を追加する形で拡張できます。

### 既知の制限（今後の課題）

同一トリップに対する同時編集は「後勝ち」（last-write-wins）です。個人利用のMVPとしては十分な整合性ですが、複数人が同じ旅行を同時に編集するようなユースケースを想定する場合は、トランザクション（`SELECT ... FOR UPDATE`等）を用いた排他制御への強化を検討してください。

### Next.jsのルートキャッシュについて(重要)

`app/api/**/route.ts` には全て `export const dynamic = "force-dynamic";` を明示しています。これが無いと、DBを直接読み書きするだけ(内部で`fetch()`を使わない)のルートハンドラは、Next.jsの自動判定によりVercel上で**静的にキャッシュされてしまい**、DBへの保存自体は成功しているのにAPIのレスポンスが更新されない(＝画面に反映されない)という不具合が起きます。ローカルの`next dev`では全ルートが動的実行されるため気づきにくく、Vercel本番でのみ発生する点に注意してください。新しくAPIルートを追加する際も、この設定を必ず入れてください。

さらに、`export const dynamic = "force-dynamic"` だけではVercelのエッジ/CDN層でのキャッシュを防ぎきれない場合があったため、`GET /api/trips` と `GET /api/trips/:tripId` のレスポンスには明示的に `Cache-Control: no-store, no-cache, must-revalidate, max-age=0` ヘッダーを付与しています。同様の「DBには保存されているのに一覧に出てこない」症状が再発した場合は、他のGETルートにも同じヘッダーを追加してください。

`lib/db.ts` の `readTripPlaces`/`writeTripPlaces` には診断用の `console.log` を仕込んでいます。同様の不具合が起きた場合は、Vercelダッシュボードの「Functions」→対象関数の「Logs」で `[db] readTripPlaces` / `[db] writeTripPlaces` の行を確認すると、実際にDBから何件取得できているかがすぐ分かります。

**この`Cache-Control`ヘッダーは、全てのGETルート（場所検索・各種エクスポート・周辺駐車場検索を含む）に適用済みです。** 「プランは作成済みなのに『プランが見つかりません』と表示される」「周辺駐車場が表示されない」といった症状も、同じくGETレスポンスがキャッシュされていたことが原因でした。新しくGETルートを追加する際は、必ず同様に `Cache-Control: no-store` をレスポンスへ明示してください（エラーレスポンス側も忘れずに。404等のエラー応答がキャッシュされ、後で状態が変わっても古いエラーが返り続けるケースがあるため）。

サーバー側のヘッダーに加えて、**フロントエンドの`fetch()`呼び出し側にも `{ cache: "no-store" }` を明示しています。** サーバーが正しいヘッダーを返すようになる前に一度ブラウザがレスポンスをキャッシュしてしまっていた場合、サーバー側だけ直しても、ブラウザ側のキャッシュが残ったままだと症状が再現し続けることがあります。新しくAPIを呼び出す`fetch()`を追加する際は、GETリクエストには基本的に `cache: "no-store"` を付けてください。

### Google Maps Platformの利用規約への対応

Googleの各APIポリシーでは、**Place IDのみ無期限保存が許可**されており、それ以外の内容（名称・住所・座標・写真・評価・駐車場情報等）は原則キャッシュ・保存禁止です（Routes APIの座標に限り最大30日間の一時キャッシュのみ例外）。

このアプリでは、生成した旅程プランについても **Place IDと自社で計算した時刻・料金などの数値のみをDBに保存し、名称・座標・駐車場候補などのGoogle由来の表示情報は一切保存していません**。画面表示・エクスポート（Word/Excel/PDF/カレンダー/KML）のたびに、`lib/plan-view.ts` の `buildPlanView()` がPlace IDから最新の情報をGoogleに都度問い合わせて表示用データを組み立てます。駐車場候補も、一覧を開くたびにその場で検索するだけで保存しません。

## モバイルアプリ(Capacitor)構成

Web版（Vercel）とAndroid/iOSアプリで**同じNext.jsコードベースを共有**しつつ、Capacitorアプリ側は「サーバーを持たない静的シェル」として動かす構成にしている。

```
┌─────────────────────────────┐
│ Vercel(バックエンド兼Web版)    │
│ app/api/** … Neon Postgres /  │
│   Google Maps APIを呼ぶ処理   │
│ app/page.tsx 等 … Web版として │
│   そのまま配信                │
└─────────────────────────────┘
        ▲ HTTPS (絶対URL)
┌─────────────────────────────┐
│ Capacitorアプリ(iOS/Android)  │
│ out/ に静的書き出ししたHTML/JS │
│   を端末内に同梱して即座に表示 │
│ データはVercelのAPIを           │
│   絶対URL+X-Device-Idで呼ぶ    │
└─────────────────────────────┘
```

### なぜこの構成か(App Store 4.2対策)

`capacitor.config.ts` の `server.url` にVercelの本番URLを設定して「リモートページを丸ごと表示するだけ」にする構成は、App Store審査ガイドライン4.2(Minimum Functionality)で「Webサイトの単なるラッパー」と判定されやすい。そのため、HTML/JS自体は端末にビルド同梱し、データ取得だけをAPI経由で行う構成にしている。

### 主要な設計判断

- **`app/api/**` はモバイルに同梱しない**：Route HandlerはNext.jsの`output:'export'`(静的書き出し)と共存できないため、モバイル向けビルド時だけ `scripts/build-mobile.mjs` が一時的に `app/api` を退避してからビルドする(Vercel向けビルド `npm run build` には一切影響しない)。
- **旅程詳細ページを2つのラッパー+共通コンポーネントに分離**：`components/TripDetailScreen.tsx` に画面ロジックを集約し、Web版は `app/trips/[tripId]/page.tsx`(パスパラメータ)、モバイル版は `app/trip/page.tsx`(`?id=`のクエリ文字列)から呼び出す。tripIdはNeon Postgres上の実行時データでビルド時に列挙できないため、`app/trips/[tripId]` に`generateStaticParams()`を書いて無理に静的生成しようとするのではなく、**モバイル向けビルド時に `app/trips` ディレクトリ自体を `scripts/build-mobile.mjs` が一時退避してビルド対象から除外**する方式にしている。モバイル版では `app/trip/page.tsx` が実行時にクエリ文字列からtripIdを受け取り、Vercelの `/api/trips/:tripId` から都度データを取得する。
- **fetch呼び出しは全て `lib/api-base.ts` の `apiFetch`/`apiUrl` 経由**：Web版では相対パスのまま、モバイル版はビルド時の`NEXT_PUBLIC_API_BASE_URL`で絶対URLに切り替わる。あわせて `X-Device-Id` ヘッダーも自動付与する。
- **`middleware.ts` でCORSを許可**：モバイルアプリはVercelから見て別オリジンになるため、`/api/:path*` に対してCapacitorのオリジン(`capacitor://localhost`, `https://localhost` 等)を許可している。Capacitor/Ionicの既知オリジンパターンは環境変数の設定内容に関わらず常に許可し(`ALLOWED_MOBILE_ORIGINS`は追加許可のみに使う)、プリフライト(OPTIONS)には常に2xxで応答する。認証はCookieではなく`X-Device-Id`ヘッダーで行っているため、`Access-Control-Allow-Credentials`は意図的に設定していない。

### 端末ベースの簡易データ分離について(重要・暫定対応)

本格的なユーザー認証(ログイン)はまだ導入していない。認証なしのままモバイルアプリを公開すると、トップページの旅行一覧が**全利用者で共有される**状態になってしまうため、`lib/device-id.ts` で生成した端末IDを `trips.device_id` に紐付け、**一覧表示だけ**を「自分の端末が作った旅行」に絞り込んでいる。

旅程詳細ページやAPI操作自体は、これまで通りIDが分かれば端末を問わずアクセス可能なままにしている(「旅程を共有」機能でリンクを渡した相手が閲覧・編集できるようにするため、意図的に制限していない)。**本格的な複数ユーザー運用やプライバシー要件が明確になった場合は、Supabase Auth等による正式な認証への置き換えを推奨する。**

### モバイルビルドの実行手順(お手元で実行)

```bash
npm install
npm run build:mobile      # app/apiを一時退避 → output:'export'で静的書き出し(out/)→復元
npx cap sync               # out/ の内容をios/android各プロジェクトへコピー
```

`.env.local` (またはCI/CDのビルド環境変数)には、モバイルビルド時に以下を設定すること。

```
NEXT_PUBLIC_API_BASE_URL=https://<本番のVercelドメイン>
NEXT_PUBLIC_BUILD_TARGET=mobile
```

`npm run build:mobile` は内部で `BUILD_TARGET=mobile` と `NEXT_PUBLIC_BUILD_TARGET=mobile` を自動設定するが、`NEXT_PUBLIC_API_BASE_URL` は環境ごとに異なるため、事前に `.env.local` 等へ設定しておく必要がある。

**`NEXT_PUBLIC_API_BASE_URL` が未設定、または `https://` から始まらない・`localhost`を含む等の不正な値の場合、`scripts/build-mobile.mjs` はビルド自体を失敗させる。** これは、未検知のままビルドが成功してしまうと、アプリ内蔵ページの`fetch("/api/...")`がVercelではなくアプリ自身のWebView(`https://localhost`)へのリクエストになり、実機/エミュレーターで「JSONを期待した箇所にHTMLが返ってきてパースエラーになる」という原因の分かりにくい不具合につながるため(実際に発生した事例: Logcatに `SyntaxError: Unexpected token '<'` が出る等)。念のため `lib/api-base.ts` 側にも、モバイルビルドかつ環境変数未設定の場合に既知の本番URLへフォールバックする二重の安全策を入れている。

万一この対策をすり抜けてAPIベースURLの設定を誤った場合でも、`lib/api-base.ts` の `apiFetchJsonGet`/`apiFetchJson` がレスポンスの`Content-Type`を確認し、JSON以外(HTMLのエラーページ等)が返ってきた場合はその旨と応答内容の一部を含むメッセージで例外を投げるため、画面上に原因を推測しやすいエラーメッセージが表示される。
